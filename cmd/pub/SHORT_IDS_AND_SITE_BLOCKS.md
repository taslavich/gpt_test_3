# Publisher: Site ID / Zone ID по 12 символов и блокировка по Site ID

База RTB: `proj258.zip`. Второй патч — к `FProj239(1).zip` с путями
`twinbid-backend/...`, применяется из корня frontBack. Патч RTB совместим
с ранее выданным `proj258_publisher_percent_map.patch`; он не включает и
не отменяет процентную мапу.

## ID

- Hostname нормализуется прежним способом: нижний регистр, без `www.` и
  завершающей точки; путь, схема и порт не входят в Site ID.
- Site ID: SHA-256 от прежнего однозначного входа `site + hostname`, затем
  остаток от деления беззнакового хеша на `62^12`, Base62, дополнение слева `0`.
- Алфавит Base62 строго `0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ`.
- Zone ID: тот же алгоритм для `zone + site_id + ad_code_id`.
- Все ID содержат ровно 12 символов, регистр значим.
- `example.com` → Site ID `U368FL4X4rW8`; для кода `code-a` Zone ID `B09ffMQbqgLg`.
- ID сайта глобален для hostname, не зависит от владельца/рекламного кода.
  Zone ID зависит от кода, как раньше. Поддомены остаются отдельными сайтами.
- Полный `Hash()` для остальных ключей и HMAC остаются прежними.

Короткий хеш не гарантирует математического отсутствия коллизий. Используется
детерминированное 12-символьное пространство; отдельный реестр разрешения
коллизий не добавляется. 133 независимых Python golden-вектора одинаковы в
обоих проектах; также проверены нормализация, фиксированная длина, ведущие нули,
регистр и конкурентные вызовы. Выборочный тест уникальности не является
доказательством отсутствия коллизий.

ClickHouse DDL не меняется: существующие столбцы `String` принимают новые ID.
ORTB-телеметрия и исходящий запрос получают уже готовые короткие значения.
Обычные SSP, DSP, проценты, выбор победителя и финансовые обработчики не меняются.

## Блокировка

URL сохраняется: `PUT /api/publisher/admin/domain-block`, теперь тело такое:

```json
{"site_id":"U368FL4X4rW8","blocked":true,"reason":"Решение администратора"}
```

`blocked:false` снимает блокировку. Поле `hostname`, доменные строки и старые
64-символьные ID отвергаются. Доступ остаётся только у настроенного
администратора с действующим JWT. Код кабинета проверяет формат и сохраняет
ID как передан, без получения данных из ClickHouse и без хеширования домена.
Если используется отдельный административный frontend, его запрос нужно
перевести с `hostname` на `site_id`; frontend в этих двух backend-патчах нет.

Новая таблица PostgreSQL `publisher_site_blocks` создаётся существующим
`EnsurePublisherSchema` при обычном запуске backend. Первичный ключ —
`site_id`, сравнение с учётом регистра (`COLLATE "C"`), проверка Base62/12.
Sync пишет готовый Site ID в отдельный Redis policy HASH
`twinbid:publisher:v1:{control}:site-blocks:v2`. Publisher вычисляет свой Site ID
и проверяет именно его. Отсутствие policy/несовпадение epoch остаётся ошибкой
503, а не разрешением трафика. Старая domain policy не служит fallback.
Блокировка Site ID действует на всех владельцев/коды на этом сайте.

Старая `publisher_domain_blocks` не удаляется, её данные не переписываются.
Старые доменные правила перестают использоваться; если они были настроены,
внесите их заново по новым Site ID перед включением трафика. В согласованном
сценарии Publisher-трафика и накопленной статистики пока нет, поэтому перенос
истории и старых frequency/reservation-ключей не выполняется.

## Порядок установки без Publisher-трафика

1. Применить оба патча к соответствующим исходникам.
2. Собрать и обновить backend кабинета. Дождаться успешного Sync новой policy.
   Существующую процедуру контроля epoch/readiness не обходить.
3. Собрать и обновить Publisher-сервис RTB (`cmd/pub`).
4. Проверить Site ID на запросе, административную блокировку/разблокировку,
   затем включать трафик. Во время смешанных версий новая блокировка может
   ещё не применяться старым Publisher, поэтому трафик включать после обновления.

Новые ENV и ручное применение ClickHouse DDL не требуются. Административные
JWT/права, синхронизация кодов, выплаты и `RunRevenueSync` не изменяются.

## Проверки

Тесты запускаются с `-race` и отдельным локальным Redis. Проверены реальный
HTTP Publisher, передача Site ID в SSP, существующая цепочка admission/commit,
ORTB-поля, блокировка разных кодов одного сайта, разблокировка, изоляция сайтов,
регистр, неправильный epoch и отсутствие новой policy.

Backend-тесты используют реальный JWT middleware и Redis; SQL-взаимодействия
API и Sync проверяются через тестовый `database/sql/driver`, без новых
зависимостей. Это не выполнение SQL на настоящем PostgreSQL. PostgreSQL-
интеграционные тесты требуют `PUBLISHER_TEST_POSTGRES_DSN` и отдельно отмечаются
как пропущенные, если тестового PostgreSQL нет.

Известный прежний тест `TestPublisherOnlyAcceptsTrustedNginx` создаёт Server
без инфраструктурной конфигурации и паникует при регистрации `GET `.
Падение воспроизведено также на чистом proj258. Тест и production-код этой
посторонней функции не исправляются; остальные Publisher-тесты запускаются
с явным `-skip '^TestPublisherOnlyAcceptsTrustedNginx$'`.
