# Мапа процента по Publisher (proj258)

Отдельная настройка ADV: UUID владельца Publisher → удерживаемая доля TwinBid.
Как в процентной мапе Bid Engine, значения задаются долями: `0.10` = 10%,
`1` = 100%. Можно объединять UUID через запятую. Повторы после разворачивания
отклоняются. `ALL` и общий процент по умолчанию не поддерживаются: только явно
указанные владельцы. Пустая мапа `{}` сохраняет прежние правила ценообразования.

## Хранение и управление

По умолчанию файл `publisher_percent_map.json` лежит рядом с файлом,
указанным в существующем `ADV_PERCENT_MAP_FILE_PATH`. В патч включена пустая
мапа `cmd/adv/publisher_percent_map.json`.

Необязательный `ADV_PUBLISHER_PERCENT_MAP_FILE_PATH` позволяет изменить путь.
Новые ENV для запуска не обязательны. Отсутствующий файл означает пустую мапу;
невалидный существующий файл приводит к ошибке запуска ADV.

На существующем HTTP-порту ADV доступны:

- `GET /filter/publisher_percent_map` — сохранённые ключи, включая группировку.
- `PUT /filter/publisher_percent_map` — полная замена мапы, успех HTTP 204.
- `GET /filter/debug_publisher_percent_map` — развёрнутые ключи в памяти.

PUT проверяет весь объект, атомарно сохраняет файл и только затем публикует
снимок в памяти. Ошибка проверки — HTTP 400, ошибка записи — HTTP 500;
прежний снимок при этом сохраняется. Одно значение фиксируется на весь аукцион.
Нулевой процент — полноценная запись, а не отсутствие настройки.
Ручная правка файла читается при следующем запуске; PUT действует сразу.
Если запущено несколько экземпляров ADV, обновите каждый через его API и
сохраните соответствующие файлы, как для существующих локальных мап.

Пример (замените ключ реальным UUID владельца, не UUID рекламного кода/кампании):

```json
{
  "11111111-1111-4111-8111-111111111111": 0.10
}
```

## Приоритет и promo

- Нет владельца в мапе: прежние мапы, promo и процентеры без изменений.
- Есть владелец: его процент выше Simple, Complex и рекламодательской мапы.
- Допускается 0–100%. При активном promo рекламодателя применяется
  `max(процент_паблишера, 0.20)`, без прибавления 20 процентных пунктов.
- После исчерпания promo возвращается заданный процент паблишера.
- Старый promo-минимум 30% остаётся для запросов без Publisher override.
- При 100% кандидат отбрасывается без записи победителя и начислений.

Для обычных кампаний Simple/«только мапа» и RTB-кампаний внутри ADV исходная
цена рекламодателя сохраняется, цена площадке = исходная цена × (1 − процент).
Обычные внешние DSP и их процентные мапы в Bid Engine не меняются.

Complex продолжает использовать SSP bid существующего ценового поиска;
его автоматически подобранная маржа заменяется ручной. Цена рекламодателя
пересчитывается по прежнему соотношению `SSP bid / (1 − маржа)` и проходит
существующую проверку баланса. Списание и исходная ставка для выбора победителя
сохраняют существующие правила. При 100% деление не выполняется.

Запросы с ручной маржой не помечаются как результаты автоматической пробы
(`point_version=0`), чтобы не искажать обучение процентера. Существующий ценовой
поиск Complex не переписывается; его текущая SSP-цена продолжает использоваться,
но трафик с ручной маржой не обучает обычные пробы. После удаления записи вновь
используется обычная точка процентера. Состояния других паблишеров не заменяются.

## ID владельца и развёртывание

SSP Adapter после существующих проверок подписи и UUID читает `pub_user_id`
из уже созданного Publisher ORTB HASH. Не создаются новые ключи или хранилища,
TTL не меняется. Для обычного SSP дополнительного Redis-чтения нет.
ID передаётся внутренним protobuf-полем по цепочке SSP → Orchestrator → Router
→ ADV; `site.publisher.id` и `user.id` не используются для выбора процента.
Ошибка чтения атрибуции не должна незаметно обходить настроенный процент:
такой Publisher-запрос получает существующую обработку ошибки/HTTP 503.

Нужно пересобрать и обновить четыре сервиса: ADV, Router, Orchestrator,
SSP Adapter. Сгенерированные protobuf-файлы уже включены; protoc при сборке
не требуется. Обновляйте получателей раньше отправителей: ADV → Router →
Orchestrator → SSP Adapter. Сначала оставьте мапу пустой, затем задайте процент
после обновления всей цепочки. Старые версии игнорируют новое protobuf-поле;
при смешанных версиях override может ещё не применяться.

Backend кабинета, frontend, ClickHouse DDL, loader, финансовые обработчики,
Outbox и очереди Publisher не изменяются.

## Сборка и тесты

Из корня RTB:

```sh
go build -o ./bin/adv ./cmd/adv
go build -o ./bin/router ./cmd/router
go build -o ./bin/orchestrator ./cmd/orchestrator
go build -o ./bin/spp-adapter ./cmd/spp-adapter
```

Новые тесты: хранение/группировка/валидация/перезапуск/ошибки записи;
конкурентное обновление; promo и его исчерпание; все три режима и RTB-кампании
ADV; 0%, 20%, 21%, 95%, 100%; сохранение SSP-цены Complex; обычный трафик и
изоляция владельцев; реальный аукцион и запись цены победителя; HTTP API;
protobuf и подписанная цепочка SSP → Orchestrator → Router.

```sh
# Redis должен быть отдельным тестовым экземпляром, без production-данных.
PUB_TEST_REDIS_ADDR=127.0.0.1:16379 go test -race -count=1 \
  ./internal/services/adv/service ./internal/services/adv/web \
  ./internal/services/dspRouter/web ./internal/services/orchestrator/web \
  ./internal/services/sspAdapter/web -run 'TestPublisher|TestSignedPublisher'
```

Тесты используют DB 13/14 и существующие тестовые DB; без переменной
Redis-интеграции явно пропускаются. Для запуска в проверке патча использовался
отдельный локальный Redis; production не использовался.

Известная ошибка исходного proj258: полный пакет ADV падает в
`TestDiagnosticDefinitionsAreCompleteAndCodesUnique` из-за повторного кода 330.
Воспроизведено также на чистом архиве; этот патч её не исправляет.
`go vet` Router выявляет прежнее копирование protobuf с mutex в
`domain_http_handlers_test.go:156`; этот файл не меняется.
Проверки с настоящим ClickHouse и необязательный latency benchmark не выполнены.

Фактическая проверка на этой версии: 192 целевых теста/подтеста с `-race`
прошли; все 10 новых основных тестов прошли, новые Redis-интеграции не
пропущены. В расширенном прогоне восьми пакетов: 609 успешных тестов/подтестов,
одно описанное выше прежнее падение диагностики и два пропуска внешних проверок.
Тесты `cmd/adv`, сборка четырёх сервисов и `git diff --check` прошли.
Обычный vet прошёл для остальных проверенных пакетов; Router прошёл остальные
анализаторы при `-copylocks=false`. Полный vet Router остаётся с прежней ошибкой,
подтверждённой на чистом proj258. Это не объявляется успешным полным vet.
