# proj246 — безопасное обновление Publisher DDL на действующем ClickHouse

Новый код НЕ пересоздаёт и НЕ переименовывает `ads.agg_stats`. На действующей
базе он не вызывает старый полный `CreateDB`, который содержал `DROP VIEW`
и двухчасовое `DELETE/INSERT` для IPP. Эти операции остаются только в пути
первого создания ПУСТОЙ базы.

## Существующая база

При обычном запуске ClickHouse Loader проверяет структуру `agg_stats` и
наличие новых Publisher-сущностей. Допустимы только точный старый ключ
(через `os_version`) или новый ключ (с `pub_user_id`, `ad_code_id`, `zone_id`,
`pop_revenue_bucket`). Для старого ключа код проверяет, что все существующие
Publisher-колонки содержат только пустые значения. После этого удаляются
**только эти пустые колонки**, затем одним `ALTER` они создаются заново вместе
с расширением `ORDER BY`. `ssp_revenue_views`, суммы, рекламные измерения и
исторические строки не удаляются.

Существующие финансовые materialized views обновляются через
`ALTER TABLE ... MODIFY QUERY`. Их объекты, источники, цели и исторические
строки сохраняются. Publisher POP ещё не запускался: никакого переноса старых
Publisher-начислений, таблицы версий дохода или исторического backfill нет.
Начисления будущих Publisher POP событий продолжают идти из `fact_clicks`.

Выполненное **обновление DDL** фиксируется в `publisher_schema_versions` (версия
246). Это технический маркер схемы, не маркер начислений. Повторные запуски
не обновляют заново финансовые MV и не пересчитывают IPP.

Если `agg_stats` содержит нестандартный ключ, не тот тип или непустые
Publisher-атрибуты, миграция отказывается менять таблицу. Нет ни `DROP TABLE`,
ни `RENAME TABLE`, ни `TRUNCATE TABLE`, ни `INSERT SELECT` в `agg_stats` на
действующей базе. Восстановление такого нестандартного состояния требует
отдельного анализа, а не рискованной автоматической догадки.

Диагностика Publisher применяется автоматически, когда её нет, отдельно от
финансового DDL. Её ошибка регистрируется, но не прерывает финансовую ingestion.

## Запуск

Обычный старт ClickHouse Loader сам выполняет нужный DDL. `--schema-only`
также проходит через безопасный путь: для существующей базы старый полный
`CreateDB` не используется. `--publisher-pop-repair` по-прежнему является
явной аварийной операцией для восстановления пропущенных **будущих** событий
из `fact_clicks`, а не миграцией старых Publisher POP начислений.

## Проверка

- `git apply --check` и `git apply` из корня исходников proj246.
- `go test ./internal/services/clickhouse-loader ./cmd/clickhouse-loader`
- Для теста живого in-place `ALTER`: `PUBLISHER_TEST_CLICKHOUSE_ADDR=HOST:PORT
  go test ./internal/services/clickhouse-loader -run TestPublisherLegacyAggKeyPreservesHistoricalAdvertiserMoney -count=1`
- До выката на финансовый production требуется бэкап и проверка на том же
  релизе ClickHouse, что используется на сервере. Без этого нельзя обещать
  доказанную корректность `ALTER` и `MODIFY QUERY` для данной версии сервера.
